# Event-Driven Microservice Communication (2 Services)

## Use Case: Order Service ↔ Payment Service

When a user places an order, the system processes payment **asynchronously using events** instead of direct API calls.

---

## Architecture Overview

```
User → Frontend → Order Service → Event Bus (Kafka)
                                      ↓
                               Payment Service
                                      ↓
                              Event Bus (Kafka)
                                      ↓
                               Order Service
```

---

## Flow

1. User clicks **"Place Order"**
2. Frontend sends request to **Order Service**
3. Order Service:

   * Creates order with status = **PENDING**
   * Publishes event: **OrderCreated**
4. Payment Service:

   * Consumes `OrderCreated`
   * Processes payment
   * Publishes:

     * `PaymentSucceeded` OR
     * `PaymentFailed`
5. Order Service:

   * Consumes payment result event
   * Updates order status accordingly
6. Frontend fetches updated order status

---

## Event Definitions

### OrderCreated Event

```json
{
  "eventType": "OrderCreated",
  "orderId": "123",
  "userId": "u1",
  "amount": 500
}
```

### PaymentSucceeded Event

```json
{
  "eventType": "PaymentSucceeded",
  "orderId": "123",
  "paymentId": "p987"
}
```

### PaymentFailed Event

```json
{
  "eventType": "PaymentFailed",
  "orderId": "123",
  "reason": "Insufficient funds"
}
```

---

## Responsibilities

### Order Service

* Creates order
* Publishes `OrderCreated`
* Listens for payment result
* Updates order status

### Payment Service

* Listens to `OrderCreated`
* Processes payment
* Publishes result event

### Kafka (Event Bus)

* Stores events durably
* Enables asynchronous communication
* Allows multiple consumers

---

## Key Characteristics

| Feature            | Description               |
| ------------------ | ------------------------- |
| Communication Type | Asynchronous              |
| Coupling           | Loose                     |
| Reliability        | High (events are durable) |
| Scalability        | High                      |
| Response Time      | Not immediate             |

---

## When to Use This Approach

* No need for instant response
* High scalability required
* Multiple services depend on same event
* System should tolerate failures and retries

---

## Advantages

* Decoupled services
* Better fault tolerance
* Easy to scale independently
* Supports event replay and recovery

---

## Trade-offs

* Increased complexity
* Eventual consistency (not immediate)
* Debugging is harder than synchronous flow

---

## Comparison with Synchronous Approach

### Synchronous (REST)

```
Order Service → Payment Service → Response
```

### Event-Driven

```
Order Service → Event → Payment Service → Event → Order Service
```

---

## Interview Summary

“In this design, the Order Service publishes an `OrderCreated` event instead of directly calling the Payment Service. The Payment Service processes the event and emits a result event. The Order Service listens and updates the order status. This approach provides loose coupling, better scalability, and improved reliability at the cost of eventual consistency.”

---

## One-line Summary

**Order Service emits event → Payment Service processes → sends result event → Order Service updates state.**
